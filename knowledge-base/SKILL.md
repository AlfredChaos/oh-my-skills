# Knowledge Base — LLM驱动的Obsidian知识管理

基于 Andrej Karpathy 的 LLM Knowledge Bases 方法论，将 Obsidian 知识库改造为
LLM可编译、可查询、可增量增强的结构化知识系统。

## 核心原则

1. **LLM写，你看** — 知识库内容由LLM维护，人负责选题和质量审查
2. **每次探索都沉淀** — Q&A和分析结果回流wiki，不做一次性消费
3. **渐进式增长** — 不追求完美，先跑起来，在用中进化
4. **raw/与wiki/分离** — 原始数据不可变，wiki是衍生品，可随时重新编译
5. **善用工具链** — Claude Code + MCP + Obsidian 覆盖全流程

## 三层目录架构

```
<vault-root>/
├── raw/                    # 第一层：原始数据（不可变）
│   ├── articles/           #   网页文章（Web Clipper或webReader导入）
│   ├── papers/             #   论文/技术文档
│   ├── videos/             #   视频转录/笔记
│   ├── repos/              #   第三方仓库数据
│   └── images/             #   本地图片资源
├── wiki/                   # 第二层：编译后的结构化知识
│   ├── index.md            #   总索引（LLM自动维护）
│   ├── concepts/           #   概念文章（LLM从raw/提炼生成）
│   └── summaries/          #   文档摘要（每篇raw/内容对应一份）
├── output/                 # 第三层：衍生输出
│   ├── qa/                 #   Q&A结果归档（查询即积累）
│   ├── slides/             #   Marp幻灯片
│   └── visualizations/     #   图表/可视化
└── _templates/             # 模板文件
    └── concept-template.md # 概念文章模板
    └── summary-template.md # 摘要模板
```

## 工作流

### 工作流1：初始化/迁移（init）

对现有知识库进行首次结构化改造。

**步骤：**

1. **扫描现状** — 列出vault根目录下所有文件和目录，识别内容类型
2. **创建骨架** — 建立 raw/、wiki/、wiki/concepts/、wiki/summaries/、output/、output/qa/ 目录
3. **分类迁移** — 将现有内容按类型迁入对应位置：
   - 未经处理的原始来源（视频笔记、第三方仓库数据）→ raw/ 对应子目录
   - 已分析/加工的内容 → wiki/summaries/ 或 wiki/concepts/
   - 报告/测试等一次性产出 → 保留原位或归入 output/
4. **生成索引** — 扫描所有 .md 文件，生成 wiki/index.md：
   - 按主题分类
   - 包含每篇文档的一句话摘要
   - 使用 Obsidian `[[双链]]` 语法
   - 标注最后更新日期
5. **写入_templates/** — 创建概念文章模板和摘要模板
6. **Git提交** — 将迁移结果提交到版本控制

**迁移规则：**
- 不删除任何原始文件，只移动或创建
- 移动文件时保留git历史（用git mv）
- 迁移后验证所有文件可访问

### 工作流2：数据摄入（ingest）

将新内容导入知识库。

**步骤：**

1. **接收来源** — 识别用户提供的内容类型：
   - URL → 用 `mcp__web_reader__webReader` 或 `mcp__tavily-mcp__tavily-extract` 转为markdown
   - 文件 → 复制到 raw/ 对应子目录
   - 文本 → 直接写入 raw/ 对应子目录
2. **保存原始数据** — 写入 raw/ 的对应子目录，文件名格式：`YYYY-MM-DD-<简短描述>.md`
3. **触发编译** — 自动执行工作流3（compile）处理新数据

### 工作流3：知识编译（compile）

将 raw/ 中的原始数据编译为结构化知识。

**步骤：**

1. **扫描raw/** — 找出尚未编译的新内容（通过比对 wiki/summaries/ 中的文件列表）
2. **生成摘要** — 为每篇新内容生成摘要文件到 wiki/summaries/：
   ```markdown
   # <标题>
   > 来源：[raw/xxx](路径) | 日期：YYYY-MM-DD

   ## 摘要
   <3-5句话的核心要点>

   ## 关键概念
   - [[概念A]]
   - [[概念B]]

   ## 原文链接
   - [来源](url)
   ```
3. **提取概念** — 识别新内容中的关键概念，对每个概念：
   - 若 wiki/concepts/ 中已有 → 更新补充新信息
   - 若不存在 → 创建新概念文章
4. **更新双链** — 确保所有 `[[双链]]` 指向正确
5. **更新索引** — 更新 wiki/index.md，反映新增内容
6. **Git提交** — 提交编译结果

### 工作流4：问答（qa）

对知识库进行提问，答案回流增强wiki。

**步骤：**

1. **理解问题** — 分析用户提问涉及哪些概念和文档
2. **检索相关内容** — 读取 wiki/ 和 raw/ 中的相关文件
3. **生成答案** — 综合分析后给出回答
4. **沉淀结果** — 将有价值的问答结果写入 output/qa/，格式：
   ```markdown
   # Q: <问题>
   > 日期：YYYY-MM-DD | 相关概念：[[概念A]], [[概念B]]

   ## 回答
   <详细回答>

   ## 新洞察
   <如果问答中产生了新认知，记录于此>

   ## 建议补充
   <基于此问答发现的知识缺口>
   ```
5. **回流wiki** — 如果问答产生了新认知，更新相关概念文章

### 工作流5：健康检查（lint）

定期检查知识库的数据完整性和质量。

**步骤：**

1. **断链检查** — 扫描所有 `[[双链]]`，找出指向不存在文件的情况
2. **孤立检测** — 找出没有被任何双链引用的文件
3. **一致性检查** — 对比不同文档中同一概念描述是否矛盾
4. **缺口发现** — 识别知识图谱中的空白区域，建议补充方向
5. **生成报告** — 将检查结果写入 output/qa/health-check-YYYY-MM-DD.md

## 模板

### concept-template.md

```markdown
# <概念名称>

## 定义
<一句话定义>

## 核心要点
- 要点1
- 要点2

## 与其他概念的关系
- [[相关概念A]] — 关系说明
- [[相关概念B]] — 关系说明

## 参考资料
- [[摘要文件名]]

---
> 最后更新：YYYY-MM-DD | 由LLM自动维护
```

### index.md 结构

```markdown
# 知识库索引

> 由LLM自动维护 — 最后更新：YYYY-MM-DD

## 概念索引
| 概念 | 文件 | 最后更新 |
|------|------|---------|
| ... | [[概念文件]] | YYYY-MM-DD |

## 文档摘要索引
| 标题 | 来源 | 日期 |
|------|------|------|
| ... | [[摘要文件]] | YYYY-MM-DD |

## 知识图谱概览
<描述当前知识库覆盖的主要领域和主题>

## 待补充
<LLM发现的知识缺口和建议探索方向>
```

## 使用指引

- 当用户说"初始化知识库"或"迁移目录"时 → 执行工作流1（init）
- 当用户提供URL/文件/文本要求导入时 → 执行工作流2（ingest）
- 当用户说"编译"、"更新知识库"时 → 执行工作流3（compile）
- 当用户对知识库提问时 → 执行工作流4（qa）
- 当用户说"检查知识库"、"健康检查"时 → 执行工作流5（lint）
- 当用户不确定该做什么时 → 建议从init开始
